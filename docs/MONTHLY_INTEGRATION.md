# Подключение месячной модели

## Что готово

В runtime/real/models находятся sensor.joblib, sensor.json, infrastructure.joblib и infrastructure.json. Имена соответствуют загрузчику сервиса. Оба направления используют одни и те же обученные веса LightGBM; различаются фильтры оборудования и метрики. Это не две отдельно обученные модели.

Таргет: новое зарегистрированное начало эпизода «Неисправен» в интервале [t+24 часа, t+31 день). Модель не подтверждает физическую поломку. Backend берёт окно из метаданных; интерфейс показывает фактические даты.

## Установка

1. Скопируем все файлы из поставки поверх соответствующих путей проекта. Не удаляем остальные файлы проекта. Рабочую operations.sqlite3 не заменяем.
2. Установим зависимости: `python -m pip install -r requirements.txt`.
3. Для локального запуска выполним `start.cmd real`. Если сервер уже работал, перезапустим его.
4. Для Docker установим APP_MODE=real в существующем .env и выполним `docker compose up --build -d`. При использовании docker/wheels обновим офлайн-зависимости командой `python -m scripts.download_docker_wheels` перед сборкой. Новая обязательная зависимость: lightgbm==4.7.0.
5. Проверим GET /api/models: target_monthly, horizon 24/744, version monthly-*. GET /api/health должен возвращать mode=real.

Переобучение не требуется. Не запускаем scripts.train для установки этого комплекта: эта команда обучает прежний суточный baseline и перезапишет модели.

Обязательно переносим backend/ml/monthly_adapter.py вместе с joblib. Он нужен при распаковке модели. Новый scoring.parquet содержит полный набор признаков. Старый scoring.parquet для этой модели не подходит. Только четырёх файлов models недостаточно.

## Проверки

Прогнозы адаптера совпали с исходной функцией на применимых строках исходного среза. Срез API содержит 6145 каналов, 6012 доступны для оценки. Дата среза: 01.07.2026; это исторический пример, не текущий мониторинг.

В отдельной временной базе проверены запуск FastAPI, оба пакетных endpoint, совпадение пакетных прогнозов со срезом, месячные даты, отсутствие оценки для неприменимых строк, отказ при несовпадении признаков, повторный расчёт без дублирования, dashboard, objects, data-quality и CSV. Команда: `python -m scripts.check_monthly_integration`. Она не изменяет рабочую SQLite.

Существующие восемь тестов tests/test_api.py проходят. TypeScript проверен, Vite-сборка выполнена через `node node_modules/vite/bin/vite.js build --configLoader runner`: обычный загрузчик конфигурации столкнулся с ограничением доступа среды. Docker и развёрнутый сервер команды здесь не запускались. Проверки Python выполнялись в Python 3.13 с окружением обучения; окружение сервиса Python 3.12 необходимо проверить после установки. Joblib хранит собственный адаптер и текст LightGBM, а не sklearn-estimator.

## Метрики

| Выборка | Precision | Recall |
|---|---:|---:|
| Полная проверка ноутбука | 65,67% | 65,51% |
| Направление sensor сервиса | 40,81% | 18,86% |
| Направление infrastructure сервиса | 77,49% | 96,56% |

Направления сервиса охватывают не все типы полной проверки, поэтому общие метрики не равны их среднему. Порог везде 0.4318047559853715. Метрики направлений пересчитаны по сохранённым прогнозам, порог по ним не подбирался. Фильтры типов взяты из существующего backend. Полный отчёт проверки находится в reports/monthly_integration_check.json.

Требования по Precision для всей модели и направления датчиков не выполнены. Для газовых датчиков нет верных предупреждений. Низкий балл не подтверждает исправность. В группе насосов высокая доля положительных строк делает постоянное предупреждение сильным простым ориентиром. Отдельные месяцы заметно хуже общего результата.

Проверка 2026 года ретроспективная: период уже рассматривался при разработке. Строка оценки соответствует каналу и дате, пересекающиеся месячные окна не являются независимыми авариями. Оценка условна на полноту будущего окна. Прогнозируется любой эпизод внутри окна, а не обязательно первый после момента прогноза. Воспроизводимость обучения с нуля относительно предыдущего сохранённого варианта не устранена этой интеграцией.

## Новые данные

POST /api/predict/{direction} принимает готовые признаки в точном составе GET /api/models. Одних исходных сообщений недостаточно. Признаки должны быть рассчитаны строго до полуночи момента прогноза; будущие события не должны попадать во вход.

Для нового подготовленного data_handoff выполним из корня проекта:

```text
python -m scripts.export_monthly --handoff PATH_TO_DATA_HANDOFF --planning PATH_TO_PLANNING_ARTIFACTS --destination runtime/candidate/real
```

Команда не переобучает модель, а рассчитывает дополнительные признаки по истории эпизодов и создаёт совместимые артефакты. Перед публикацией проверим кандидата и сохраним предыдущий комплект. SQLite не переносим и не удаляем.
